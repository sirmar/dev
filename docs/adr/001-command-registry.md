# ADR 001: Command registry as single source of truth

**Status:** Accepted  
**Date:** 2026-05-02

## Context

`dev` has two concerns that must stay in sync: which commands are valid for a given repo type, and what shell completions to offer. Originally, the repo-type permission matrix existed in two places — the runtime dispatcher and `cmd_completions` — and the completion files were maintained by hand alongside the command list. Any addition or removal of a command required edits in multiple spots and risked drift.

## Decision

Centralise everything in two registry functions in `dev.sh`:

- `_DEV_COMMANDS` — ordered array of every subcommand
- `cmd_repo_types <cmd>` — returns the space-separated list of repo types that may run a command, or `*` for universal commands
- `cmd_args <cmd>` — returns static completion arguments for a command

The runtime dispatcher and `cmd_completions` both read from these functions. Shell completions are generated by `src/generate-completions.sh`, which sources `dev.sh` and iterates the same registry — there is no hand-maintained copy.

`mdev.sh` follows the same pattern with `MDEV_COMMANDS` and `cmd_arg_type`.

## Consequences

- Adding, removing, or restricting a command requires a change in one place only.
- Completion files must be regenerated (via `src/generate-completions.sh`) whenever the registry changes; they are committed to the repo.
- The generator script must be kept in sync if new argument patterns are introduced that require special-cased completion logic (e.g. file arguments, service names).
